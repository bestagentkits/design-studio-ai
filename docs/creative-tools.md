# Creative boards and layered painting

The editor toolbar opens a creative board or painting studio. Boards keep smooth, pressure-sensitive ink, shapes, text and bound connectors inside an editable page embed. Paint offers bristle, dry brush, wash, smudge and eraser using the same pixel engine as the approved drawing lab. Each completed gesture joins project undo/redo. Close the workspace and Save; Live mode persists completed local edits after the creative workspace closes. In-flight Live responses wait until close before reconciling. Uploading tiles alone does not save a project revision.

## Document and agent contract

[Document schemas](../src/shared/schema.ts) read v1 and v2. Creating a board or painting upgrades the current document; ordinary legacy edits keep v1. The pure [upgrade](../src/shared/document-upgrade.ts) preserves IDs, page layout and project kind. Undo does not downgrade v2 or reuse a painting generation. A stored v2 project rejects v1 saves and merges, including requests with a current revision.

Use `dsa schema --operations`, MCP `studio://operations`, or browser `studio_capabilities` for exact [shared operations](../src/shared/board-operations.ts): add boards/paintings, upsert/remove board elements, and replace a painting at its observed generation. REST document PUT, MCP `update_document`/`patch_document`, CLI document operations and WebMCP use these same validators. Pixel operations consume registered immutable assets; structured text from a provider is not a pixel renderer. The browser supplies real pressure when available and estimates mouse pressure from movement speed.

Paint source is an ordered layer manifest of immutable 512×512 RGBA8 PNG tiles, with checksums, dimensions, visibility, opacity, blend mode, masks and clipping settings. The [compositor](../src/shared/paint-composite.ts) supports normal, multiply, screen and overlay in sRGB; groups apply visibility and opacity to their member layers. The server verifies PNG dimensions/checksums and builds the persisted composite itself. It does not trust an uploaded preview. Brush pickup samples the frozen visible composite while deposits affect the selected layer. Layer controls include naming, ordering, duplication/deletion, visibility, locking, opacity, blend, alpha lock and clipping. Same-painting concurrent source/settings edits conflict as a whole; a composite-only server refresh is not a source edit. Independent board elements and separate paintings can merge.

Painting saves accept optional `operationId` in document PUT. Retry the same ID, exact document and expected revision after an uncertain response; a changed payload with that ID conflicts. Without an explicit ID, an exact retry derives the same identity from its payload and revision. The latest eight successful painting-save receipts per project are retained. Older retries receive a revision conflict; re-read and reconcile rather than guessing a revision. Brief approval remains separate.

## Assets and public output

The [asset lifecycle](../server/asset-lifecycle.ts) atomically reserves in-flight upload bytes against 2 GiB per project and 8 GiB per owner, including retained assets. Painting processing admits one job per owner and two per installation with a 60-second processing lease. A save is bounded to 64 megapixels of changed composite output and 512 megapixels of source tile/mask input before processing starts. Failed operations leave the last saved document intact. Uploaded immutable assets are retained until project deletion; automatic tile/history garbage collection is not enabled. Storage limits therefore include abandoned uploads and old undo assets.

Publication and shared exports use a [render projection](../src/shared/public-creative-projection.ts). It replaces painting sources with the verified visible composite and removes hidden board elements and their private assets. Public asset routes authorize only assets in that projection. JSON export remains the private editable document; it is not a portable asset archive. Clone copies owned bytes and remaps nested references. Duplicating an embed creates independent editable content while sharing immutable bytes safely.

Board/painting-dependent compositions cannot yet be packaged in reusable design-system libraries. Applying tokens and inserting legacy compositions preserve v2 roots. Use editable page embeds or project clone for creative content.

A failed stroke or layer update retains one bounded local transaction in the open painting workspace. Retry reuses its prepared document after successful uploads; it does not rerun smudge over changed pixels. A rejected merge never overwrites newer painting data. Download PNG backup preserves the visible local result, or explicitly discard it. This recovery is in memory for the current workspace, not durable recovery across browser reload or account changes.

## Current integration boundaries

The integrated workspace is an initial production-source slice, not completion of the full creative-tools plan. The current UI starts a 512×512 painting, supports the layer controls above, and retains the four approved brush presets plus erasing. Layer groups/mask editing UI, resizing/selection/fill, diagram-family layout workflows, vector-handle editing, sticker/emoji/GIF library/playback and physical Pencil acceptance remain tracked in the [active plan](../plans/260910-1852-board-paint-diagram/plan.md). Typed model support does not imply a completed user workflow. No release or physical iPad acceptance is implied by local browser tests.

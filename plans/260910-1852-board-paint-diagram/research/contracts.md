## Recommended proposed canonical model

Adopt v2 only when first new content is committed. Read valid v1 unchanged; upgrade through an explicit shared pure transform preserving IDs, layout, timestamps and brief state. Never allow a v2 write to downgrade persisted v2 to v1. New document kinds/fields must not be silently stripped by an old parser. Unsupported clients get actionable version/capability errors, not partial data presented as success. Upgrade documents and assets within the ordinary project CAS workflow; no bulk rewrite of existing projects/publications.

The root remains one `DesignDocument`. Proposed optional v2 `boards[]` and `paintings[]` are typed sections within it, not independent databases or SDK documents. Add `board` node with `boardId` and explicit view bounds/crop; a standalone board project contains a page and board node, while slide embedding references the same in-document board. Board viewport/camera/selection/tool state stays local session state unless deliberately defined as presentation settings; multiple embeds may have independent view bounds. A board cannot recursively embed itself. Duplication policy must be explicit: ordinary duplicate creates an independent board copy; linked insertion explicitly retains the board ID.

`boards[]`: stable ID/name; typed ordered elements; finite workspace bounds separate from display/export crop. Element union covers freehand vector stroke, geometric shape, rich/plain text, sticky note, bound connector, group/frame, image/sticker/emoji/GIF and painting reference. Typed element payloads include geometry, rotation, visibility/lock, style, IDs and semantics; no arbitrary serialized SDK element blobs. Store roughness and deterministic seed if sketch rendering uses them. Emoji should retain Unicode/text semantics plus chosen deterministic visual asset when fidelity matters. GIF uses an imported asset and explicit poster/playback policy.

Connectors need stable element IDs, endpoint bindings (target ID, normalized anchor/port, offset), ordered waypoints, routing mode, arrowheads, labels and typed semantic relations. Labels are keyed child records or elements with validated ownership, not implicit SDK IDs. All requested diagram types use the same primitives and semantic graph: node role, edge role, grouping and layout intent. Mind-map parentage must be an explicitly acyclic relation; general architecture/flowchart edges may contain cycles. Connector target deletion must detach to the last computed endpoint or delete explicitly in the same operation; do not leave dangling references. Moves/grouping/duplication resolve transformed endpoint coordinates and remap bindings consistently.

`paintings[]`: stable ID/name, logical pixel width/height, color space, compositing algorithm version, ordered keyed layers, brush/paper resource references and optional derived preview descriptor. Layers have stable ID/name, visible/locked/opacity/blend mode and sparse keyed tile manifest. Tiles reference immutable registered project assets, with coordinate, dimensions and generation/hash metadata. Authoritative editable painting content is layer pixels plus this manifest. The composite is derived and keyed to the exact manifest/layer settings; it may be discarded/regenerated. Never make the SDK scene, replay log and flattened composite three competing authorities.

Advanced paint requires a real shared brush/compositor implementation: pressure/tilt sample input, spacing, brush tip/grain, paper texture, flow/opacity, eraser, wetness/loading and color mixing/smudge with bounded finite values and pinned algorithm versions. Brush commands must read prior layer pixels for mixing, with deterministic seeds where used. Keep long-term editable raster layers; do not promise individual historic stroke re-editability unless separately implemented. Browser workers can perform interactive painting; REST/MCP/CLI paint commands use the same trusted brush runtime through a server/headless execution service. Uploaded pixel commits must validate dimensions, decoded bytes, asset ownership and expected document/layer state. Agent painting must actually rasterize commands, not record descriptive commands while returning unchanged pixels.

Excalidraw/native adapter is a projection of canonical board elements. SDK internal selection/history/cache and transient in-progress stroke may exist in memory. At each completed gesture, convert to canonical typed operations, validate and commit; external agent updates regenerate the projection. Unknown SDK features fail an explicit capability check or import warning before acceptance. Required spike: full round trip of all accepted drawing/diagram/sticker element properties, stable IDs/connector labels, undo after agent edits, and editing the same board standalone and embedded. No dual-save SDK JSON escape hatch.

## Tile budgets and storage recommendation

Keep the 2000 document asset cap initially; do not silently raise every existing limit. Sparse 256-pixel tiles minimize brush mutation cost but can exceed the cap: a fully painted 2048² canvas across 12 layers is 768 tile assets, while 4096² across 12 layers is 3072. Asset accounting also includes stamps, grain, GIFs, previews and other project media. Old uploaded assets absent from `doc.assets` still occupy storage; current code has no per-asset deletion/GC endpoint.

Recommended persisted representation: 512-pixel sparse PNG/WebP tiles, with smaller in-memory dirty regions. Fully populated 2048² ×12 =192 assets; 4096² ×12 =768. Tile size is a manifest property and server-enforced allowed value, not arbitrary client input. This stays within the current cap for a useful high-quality 12-layer envelope without a new binary pack decoder. It does not make every workload fit: 4096² ×12 uncompressed RGBA is ~768 MiB before scratch/history/GPU buffers; compressed bytes may exceed 30 MiB export cap.

Before creation/resizing/layer duplication/import and each stroke commit, compute projected live assets, painted pixels, decoded bytes, dirty tile count and request bytes. Return required versus remaining budget before accepting an operation that cannot be persisted. Choose supported limits from measured desktop 16 GiB and iPad tests; start the spike with both 2048²/12-layer and 4096²/12-layer stress fixtures. A budget rejection must not erase unsaved work; allow save at original settings, export flattened copy, or user-chosen layer merge. Keep actual painting quality and multiple layers in scope. If packed layer assets are selected instead, plan a versioned safe container/parser, per-entry bounds, clone/remap/export support and partial-update cost explicitly; this is a larger storage design, not just a MIME allowlist change.

Immutable tile uploads precede document CAS. Failed/conflicting commits leave staging assets, so add bounded staged-asset cleanup with a grace period that accounts for in-flight uploads, persisted documents, publications and supported local undo retention. Never delete a referenced tile or mutate shared bytes in place. Publication links protect old tile versions; cloned projects own copies. Any DB support uses new additive migrations. Establish quotas on stored bytes, decoded pixels and concurrent paint/export work as well as schema counts; no base64 tile inflation in document JSON.

## Revision, merge and AX operations

- Add shared typed operations for board element CRUD, binding, ordering/grouping, diagram layout application, painting/layer CRUD/reordering/settings, stroke application and validated tile replacement. Server services retain ownership, revision and resource budgets. Provide structured inspect operations that return element IDs, semantic graph, layer/tile state and capabilities without dumping all bytes.
- Board/element/layer/tile arrays need stable IDs. Distinct changed tiles can merge; edits to the same tile conflict even when pixels happen to differ spatially. Never field-merge one tile's generation/hash/asset ID into an invalid combination: treat each tile record atomically. Same principle for coupled connector geometry/bindings. The generic merge implementation currently recurses records, so add domain-aware merge boundaries.
- Simultaneous paint on the same layer plus layer opacity/order changes needs explicit policy, not last-writer guessing. A stroke's input manifest or layer generation must match the current state when blending depends on it; after conflict ask/replay against newly inspected pixels only via explicit user/agent intent. Keep brief revisions untouched.
- Do not autosave each pointer event or send full base/local documents per pointer sample. Commit bounded gesture batches and dirty tiles; render live locally. Persisted CAS remains authority. Current merge requests include base+local documents and share the 21 MiB body ceiling, so size-test realistic board/stroke data, not only save payloads.
- Typed per-tool capability discovery should expose supported versions, operations, budgets, editable-versus-raster format behavior and exact recovery errors. New REST/MCP/CLI/WebMCP behavior must use the same implementations; agents should not need an Excalidraw SDK to edit a diagram or paint.

## Lifecycle and export implementation implications

Create one typed reference collector/remapper used by validation, duplication, clone, publication, export and import. Cover node/board/painting/connector/group IDs, all asset IDs including scene textures, and legacy URL fields. Asset IDs resolve exclusively through registered document assets and server ownership checks. Avoid arbitrary recursive string replacement, which could rewrite ordinary text or miss semantic references.

JSON remains structured canonical export; clearly distinguish it from a portable project package. If round-trip sharing between self-hosted instances is required, add a portable archive with canonical JSON and owned assets, strict file-count/byte/path/decompression limits, and full ID remapping on import. Existing private-URL JSON is not self-contained. Excalidraw-format import/export is an adapter boundary with a feature/loss report; generic SVG import cannot promise diagram semantic reconstruction.

Board export requires explicit crop/content bounds and output scale; embedded boards use their node viewport. Shared trusted renderer must render all board primitives, textures, paint blending and layer order for editor preview, published HTML and headless export. SVG retains supported vector objects and embeds paint raster content. PNG/PDF rasterize actual composited pixels. PPTX/Google Slides preserve supported primitives only if mapped faithfully, otherwise rasterize with truthful notices or reject unsupported target features. Existing Google policy rejects unsupported complex nodes; do not silently flatten there without a specified contract. GIF static exports need explicit poster frame/time; motion exports/playback retain animation only when actually supported and tested. No universal format parity claim.

Large paintings expose the existing 30 MiB all-assets embed cap (`server/exports.ts:84-99`), even for one selected page because embedding walks all assets. Scope reachable assets to selected pages/boards and use a validated bounded composite for static output; avoid embedding all hidden historical tiles solely because the original document references them. Portable editable export still needs full relevant layer data and its own explicit budget. Retain offline renderer isolation, fixed-origin fonts and no arbitrary user scripts.

# 3D scenes

Read [shared layout and quality](layout-and-quality.md) first. Use this for `kind: "3d"`; inspect the `object-study` template and the live schema.

## Composition and supported scene data

Establish the subject, intended viewpoint, material story, and destination format. Stage actual `model3d` nodes and `group` parents in scene space. Use `scene.position`, `scene.rotation`, and `scene.scale` for object transforms; rotations are in degrees. Set page `scene.camera` (`position`, `target`, `fov`), `ambient`, and `light` (`position`, `intensity`, `color`) for a deliberate view. Orbiting a preview is not proof that the stored camera changed.

Supported primitives are selected with `data.geometry` (box, sphere, torus, torusKnot, cone, cylinder). A `scene.mesh` uses vertex `positions`, triangle `indices`, and optional `uv`; imported GLB uses an owned asset `src`. Use `scene.material` for color, metalness, roughness, wireframe, doubleSided, or `textureAssetId`. Read actual bounds from the live schema; do not invent shader code, extra light arrays, physics, or arbitrary asset loaders.

For rigging, parent bones precede children; valid meshes need matching UV and skinning arrays, existing bone indices, and four skin indices/weights per vertex. Preserve the bind pose when inspecting animation. Use the existing mesh/UV/rig tools instead of replacing validated scene data with executable code.

## Design choices

- Prefer a clear silhouette, readable scale relationships, and intentional negative space. Check camera perspective before adding geometry.
- Light the important form; avoid blown highlights, muddy material contrast, or unnecessary high metalness. Inspect textures for seams, stretching, and resolution at the intended view.
- Keep objects and rigs only as complex as the requested effect needs. Repeated detail should add meaning rather than slow interaction.
- Flex is useful for accompanying labels, legends, or a surrounding 2D explanation. It is not a substitute for 3D transforms and camera framing.

## Review and delivery

Inspect the real WebGL scene from the delivery camera and several orbit angles. Check clipping, intersections, visibility, material appearance, texture mapping, transparent surfaces, and parent transforms. For animated rigs, inspect start/end poses and intermediate extremes; check deformations and maintain the stored bind pose. Review accompanying text for ordinary canvas overflow too. Geometry preflight alone cannot establish scene quality.

GLB/glTF carries supported scene geometry/materials and sampled animations, not the whole 2D web page or arbitrary runtime behavior. Animation export has a sampled-value budget; reduce duration, frame rate, or animated joints when the exporter reports its limit. Reopen the actual file and inspect textures, transforms, and animation.

Raster/PDF/video rendering can capture real WebGL. Keep 3D objects that need mutual depth testing together in layer order: a 2D caption separates 3D segments. Reparent/reorder through the existing operations; avoid an opaque full-page shape above a scene that should remain visible.

Material finishes are starting points; inspect the result under the delivery lighting. Texture import uses an owned asset referenced by `scene.material.textureAssetId`. When changing a material through `update-node`, preserve the rest of the `scene` object you read so transforms, meshes, or rigs are not discarded. Apply the same rule to page `scene` changes for camera and lighting.

Static SVG uses a symbolic representation rather than an actual scene screenshot. HTML can include the trusted scene viewer. Import external media before cloud export, check renderer availability, and never deliver the SVG symbol as proof of the finished 3D scene.
